================================================================================
 BYOND DM LANGUAGE LIBRARY - INTEGRATION GUIDE
 For anyone wiring this into an editor or IDE.

 LIVE DOCUMENT. Updated as features land. If something here is wrong, it is a
 bug in the doc - say so.

 ABI version at last update: 0.11  (19 exports, cdecl, six RIDs)
 Last updated: 2026-08-04
================================================================================


WHAT THIS IS
--------------------------------------------------------------------------------
  A library that reads DM (DreamMaker) source and answers questions about it.
  You embed it. It has no UI and no opinions about your editor.

  It ships as a normal native shared library with a plain C header. You do not
  need .NET installed, and you do not need to know it is written in C#.

    Windows   dm_core.dll  + dm_core.lib
    Linux     libdm_core.so
    macOS     libdm_core.dylib

  Anything with a C FFI can call it. C++, C, Rust, Python, Go, Zig, C#.


WHAT YOU GET TODAY
--------------------------------------------------------------------------------
  WORKING NOW
    - Syntax highlighting (lexical). Keywords, strings, comments, numbers,
      operators, preprocessor directives, resource literals.
    - Correct handling of the DM constructs that break naive highlighters:
      nested /* */ comments, {" multiline "} strings, "[interpolation]" holes,
      and // inside a path eating the rest of the line.
    - Unsaved buffer support. You push editor text, we analyse that, not disk.
    - MACROS ARE EXPANDED. The object tree is built from the preprocessed
      stream, so a type or var declared through a macro is the declaration
      it expands to rather than the macro's name. Codebases that declare
      through macros - which is most large ones - now resolve.
    - Autocomplete via dm_complete_at. Locals, parameters, src members,
      inherited members and BYOND builtins, with the . / : distinction the
      compiler makes. A receiver resolves when its type is written down -
      src, a typed local, a typed parameter, a literal path - and otherwise
      by inference from new / as / assignment. See the note in section 4.
    - Go to definition via dm_definition_at. Type paths, members through
      their receiver, and bare names. Returns EVERY declaration - see
      section 4, this is the part most likely to surprise you.
    - Workspace symbol search via dm_workspace_symbols. Ranked and capped,
      so a two-character query stays usable.
    - Hover via dm_hover_at. The resolved path, the declaration as written,
      and any doc comment above it - both /// runs and /** */ blocks.
    - Semantic highlighting. Colour IDs 12-15 distinguish a type name, a
      proc name, a var name and a macro name. See COLOURS below.
    - Document outline / symbols, with syntax diagnostics, via
      dm_document_symbols. Types, vars, procs and verbs, nested, each with a
      range for the whole declaration and a second range for the name alone.
    - Object tree browsing via dm_query_json. A node and its children to a
      depth, every subtype of a path, or one type's members with inheritance
      resolved. This is what a tree panel runs on. Request and response
      shapes are frozen in abi/schema/.

  NOT YET - do not design around these being absent, they are coming
    - .dmi icon states                (M8)
    - Semantic error squiggles        (M11)

  Syntax errors already arrive with the outline, in the same
  dm_document_symbols call. What is missing is the semantic layer - unknown
  types, bad member access, duplicate definitions. That is M11.


--------------------------------------------------------------------------------
 0. BUILD IT
--------------------------------------------------------------------------------
  You need the .NET 9 SDK, and on Windows the MSVC C++ build tools.

    dotnet publish src/Dm.Native/Dm.Native.csproj -c Release -r win-x64

  Valid RIDs: win-x64, win-x86, linux-x64, linux-arm64, osx-x64, osx-arm64.

  ** CALLING CONVENTION IS cdecl ON EVERY PLATFORM **
  Declared explicitly on the exports rather than left to the default. On x64
  there is only one convention and this never comes up; on 32-bit Windows
  NativeAOT would otherwise emit stdcall, which C, Rust, Go, Zig and Python's
  ctypes all assume otherwise. Include dm_core.h and call - no annotation, no
  WINAPI, no extern "stdcall". If you hand-write declarations instead, cdecl is
  what to write, and getting it wrong on x86 corrupts the stack rather than
  failing to link.

  win-x86 exists for hosts that are themselves 32-bit. It is in CI and the C++
  smoke test runs there, not merely links: cmake -A Win32 -DDM_RID=win-x86.

  ** WINDOWS GOTCHA **
  If that fails with MSB3073 and something about link.exe, the real cause is
  that vswhere.exe is not on PATH. The error message blames the linker and is
  lying to you. Fix:

    $env:PATH = "C:\Program Files (x86)\Microsoft Visual Studio\Installer;$env:PATH"

  Output lands in:
    src/Dm.Native/bin/Release/net9.0/<rid>/publish/   <- the .dll / .so
    src/Dm.Native/bin/Release/net9.0/<rid>/native/    <- the .lib (Windows)

 1. FILES YOU NEED
--------------------------------------------------------------------------------
    abi/dm_core.h        the header. this is the source of truth, read it.
    dm_core.dll          ship next to your executable
    dm_core.lib          link against this (Windows only, it is an import lib)

  There is a working CMake project at tests/abi-smoke, current with ABI 0.11 and
  passing 110 checks. It covers version negotiation, string ownership, handle
  lifetime including use-after-close, classification in both encodings,
  document symbols, completion, injected defines, go-to-definition, hover and
  workspace symbols. The include and link lines in its CMakeLists.txt are meant
  to be copied verbatim. If you are stuck on build setup, build that first and
  confirm it runs - it is 30 seconds and it separates "my build is wrong" from
  "my code is wrong".

 2. LINK IT
--------------------------------------------------------------------------------
  CMake, Windows:

    target_include_directories(myapp PRIVATE "path/to/abi")
    target_link_libraries(myapp PRIVATE "path/to/native/dm_core.lib")

    add_custom_command(TARGET myapp POST_BUILD
      COMMAND ${CMAKE_COMMAND} -E copy_if_different
              "path/to/publish/dm_core.dll" "$<TARGET_FILE_DIR:myapp>")

  Linux:

    target_link_libraries(myapp PRIVATE "path/to/publish/libdm_core.so")
    set_target_properties(myapp PROPERTIES BUILD_RPATH "path/to/publish")

  The header already has extern "C" guards. Just #include it from C++.


--------------------------------------------------------------------------------
 3. THE MINIMUM PROGRAM
--------------------------------------------------------------------------------
  This is the whole thing. Everything else is detail.

    #include "dm_core.h"

    // 1. check we agree on the ABI
    if (DM_ABI_VERSION_MAJOR(dm_abi_version()) != DM_ABI_EXPECTED_MAJOR)
        fatal("dm_core is a different major version than this build expects");

    // 2. open the project
    dm_workspace ws = NULL;
    if (dm_workspace_open("C:/games/mygame/mygame.dme", &ws) != DM_OK) {
        char *msg = dm_last_error();
        fatal(msg);
        dm_free(msg);
    }

    // 3. tell us what the build defines, before anything else asks a question
    const char *defines[] = { "CBT" };
    dm_set_defines(ws, defines, 1);

    // 4. every time the user types, push the buffer
    dm_set_buffer(ws, "code/mob.dm", utf8_text, utf8_byte_length);

    // 5. every time you paint, ask for the visible lines
    dm_classification spans = NULL;
    dm_classify_range(ws, "code/mob.dm", first_visible_line, last_visible_line,
                      DM_ENCODING_UTF16, &spans);

    int32_t n = dm_classification_count(spans);
    const int32_t *d = dm_classification_data(spans);

    for (int32_t i = 0; i < n; ++i) {
        int32_t offset = d[i * 3 + 0];
        int32_t length = d[i * 3 + 1];
        int32_t kind   = d[i * 3 + 2];
        paint(offset, length, colour_for(kind));
    }

    dm_classification_free(spans);

    // 6. at shutdown
    dm_workspace_close(ws);


--------------------------------------------------------------------------------
 4. THE CALLS, IN ORDER
--------------------------------------------------------------------------------
  dm_abi_version()
      Call first, once. Returns (major << 16) | minor. Use the
      DM_ABI_VERSION_MAJOR / _MINOR macros. Refuse to run on a major mismatch.
      A higher minor than you were built against is fine - additions only.

  dm_workspace_open(dme_path, &ws)
      Opens a project. This validates the .dme exists and records its
      directory; it does no parsing. The include graph is walked and the object
      tree is built on the first call that needs them - in practice
      dm_complete_at - and is then cached until a buffer changes.
      Returns DM_ERR_NOT_FOUND if the .dme is not there.

  dm_set_defines(ws, defines, count)                          NEW in 0.5
      Defines macros for the project, exactly as dm.exe's -D switch does.

      ** PASS WHAT THE PROJECT'S BUILD PASSES **
      The flags decide which #ifdef branches exist, so a workspace without
      them describes a DIFFERENT PROGRAM from the one the build produces:
      code behind a guard is invisible to you, or visible when it should not
      be. /tg/station, for example, builds with -DCBT.

      Spelling is the compiler's own:
        "NAME"              defined EMPTY, not 1 - matches dm.exe
        "NAME=value"
        "FN(x)=((x)*2)"     function-like

      Call it straight after opening. The object tree is lazy, so it still
      applies to your first query, and you can change flags later without
      reopening. NULL or count 0 clears them. Strings are copied.

      If your users configure build flags anywhere, plumb them through to
      this call - it is the difference between analysing their program and
      analysing a similar one.

  dm_set_buffer(ws, file, content, length)
      Tells us what the user currently has on screen for that file.

      ** ONCE YOU CALL THIS, WE NEVER READ THAT FILE FROM DISK AGAIN **
      (until dm_close_buffer). That is deliberate. Your editor is ahead of the
      filesystem on every unsaved keystroke, and disk is the wrong answer.

      `content` is UTF-8 and is copied before the call returns - you can free
      your copy immediately. `length` is in BYTES. Pass -1 if it is
      null-terminated, but prefer the real length: it avoids a scan, and DM
      string literals can legally contain a NUL.

      `file` may be absolute, or relative to the folder holding the .dme.

      Call this on every edit. It is cheap - it stores text and marks derived
      data stale. Nothing is re-analysed until you ask a question.

  dm_close_buffer(ws, file)
      User closed the tab. We go back to reading that path from disk.

  dm_classify_range(ws, file, start_line, end_line, encoding, &out)
      Line numbers are ZERO-BASED and INCLUSIVE. Out of range values clamp,
      they do not error.
      Ask only for what is visible. Asking for the whole file works but is
      wasted effort on a 10,000 line file where you are showing 60 lines.

  dm_document_symbols(ws, file, encoding, &json)
      The file's outline plus its syntax diagnostics, as one UTF-8 JSON
      document. YOU FREE IT with dm_free.

      Why JSON when classification is a packed block: symbols carry names, and
      a packed int32 block cannot express a string without a table on both
      sides. An outline is rebuilt when the file changes, not on every paint,
      so the trade goes the other way here.

      Each symbol has TWO ranges, and the difference matters:
        startLine/startChar .. endLine/endChar    the whole declaration,
                                                  members included
        selStartLine/selStartChar .. selEnd*      the NAME only

      Navigate with the sel* range. Clicking an outline entry then puts the
      caret on the identifier rather than selecting the entire block.

      kind is 0 type, 1 variable, 2 proc, 3 verb, 4 parameter. Treat an
      unknown kind as a neutral icon so a library update cannot break you.

      Diagnostics in the same document are the syntax errors for that file -
      enough for squiggles. Semantic errors arrive at M11.

      ** ONE WARNING ALREADY ARRIVES HERE: DM0300 **
      A proc block indented one level too far, into a var block, declares
      nothing at all - dm.exe compiles it with 0 errors and silently drops
      every proc under it, so calling one is a runtime error on a code path
      with a clean build. We match the compiler and declare nothing, which
      means those procs are NOT in the outline, and we warn on the header,
      which the compiler never does.

      Severity is warning, not error: the file does compile. DM03xx is that
      class - code that compiles and does not mean what it looks like -
      and more of them arrive at M11. Render them differently from the
      syntax errors if you can; this one is usually a real bug in the game.

  dm_complete_at(ws, file, line, character, encoding, &json)
      What can be typed at a position, as UTF-8 JSON. YOU FREE IT with
      dm_free. Line and character are ZERO-BASED.

      Point it at the caret. A half-typed word is not the trigger - whatever
      precedes it is - so "mob.he" completes against /mob exactly as "mob."
      does. Filter the list by the typed prefix yourself.

      "context" tells you why the list is what it is:
        Identifier      a bare word: locals, params, src members, globals
        Member          after `.` - the declared type and what it inherits
        SubtypeMember   after `:` - the above PLUS members from subtypes
        TypePath        after `/`
        None            nothing useful here

      ** DO NOT MERGE `.` AND `:` **
      They are different lists because the compiler checks them differently.
      `:` widens the check to the subtype tree; it does NOT switch checking
      off. Neither list ever contains an unrelated type's members.

      An empty list after `.` means we could not work out the receiver's
      type - typically a call result or an index. Showing everything there
      would be noise, so we show nothing.

      ** WE INFER FURTHER THAN THE COMPILER DOES. READ THIS ONE. **

      dm.exe has NO local type inference. This:

          var/x = new /obj/item
          x.hp

      is a compile error - "x.hp: undefined var" - even though hp is the
      right member of the type on the line above. Only a WRITTEN type is
      ever checked, so var/obj/item/x compiles and var/x does not, whatever
      it was initialised with. Same for `as` clauses and for assignment
      from an already-typed variable. Verified against 516.1666; the full
      matrix is in docs/dm-language-notes.md.

      We offer those members anyway. An untyped `var/x = new /obj/item` is
      almost always a declaration someone is halfway through writing, and
      the members we list are the ones they are reaching for.

      THE CONSEQUENCE FOR YOU: a user can accept one of our completions and
      get code that does not build. If that is not a trade you want to make
      in your editor, filter on it - the type we used is in each item's
      "detail" field, and you can drop Member-context items when the
      receiver is an untyped local. Tell us if you would rather have this
      behind a flag and we will add one.

      Everything else in the list agrees with the compiler. This is the one
      exception, and it is confined to completion.

      "documentation" carries the /// comment above the declaration, so a
      popup can show what a proc is for without a second call. Empty for
      builtins - nothing declares them - and empty when there is no comment.
      Both DM forms are read: a run of /// lines, and a /** ... */ block.
      A plain // or /* is NOT documentation - treating one as such would
      attach commented-out code to the declaration below it.

      Tags like @param pass through as text. DM has no doc-comment standard
      and real code spells them several ways, so render them yourself if you
      want them highlighted.

      A proc's "detail" is its signature as declared, with parameter types,
      `as` clauses and DEFAULTS: heal(mob/target, amount as num, silent = 0).
      A default tells your user the argument is optional and what it falls
      back to, which is the same information an @param comment would carry
      and cannot go stale.

      "builtin": true marks BYOND's own members rather than the project's.
      Style them apart if you like; the flag is there for that.

      ** COST ** The first call after an edit rebuilds the object tree for
      the whole project. Debounce it. Do not call it per keystroke.

  dm_workspace_symbols(ws, query, limit, encoding, &json)       NEW in 0.8
      Every symbol in the project whose name matches, as UTF-8 JSON. YOU
      FREE IT with dm_free.

      RANKED AND CAPPED, not exhaustive. A two-character query on a real
      project matches tens of thousands of symbols; unranked that is a wall,
      not a picker. Order is exact name, then prefix, then substring, with
      shorter names first inside each band. Matching is case-insensitive.

      Pass 0 for limit to take the default of 200. Ask for what you will
      actually display.

      Builtins are never returned - nothing declares them, so a hit could
      not be opened.

      "detail" is the owning path, which is what tells two `New`s apart in a
      list. Each hit carries the same two ranges as dm_document_symbols plus
      its file; navigate with the sel* range.

  dm_hover_at(ws, file, line, character, encoding, &json)        NEW in 0.7
      What to show in a tooltip, as UTF-8 JSON. YOU FREE IT with dm_free.

      Returns {} - an EMPTY OBJECT - with DM_OK when nothing resolves. A
      pointer resting on a local, a keyword or whitespace is the ordinary
      case, not a failure, so test for the "detail" key rather than the
      status code.

      Keys: detail (the resolved path), signature (the declaration as
      written), documentation (the doc comment above it, markers stripped,
      joined with newlines), and the range of the token you hovered so you
      can highlight it.

      Both DM doc forms are read: a run of /// lines and a /** ... */ block.
      A blank line or a plain // comment ends the doc run, which matches
      what a reader takes to be attached to the declaration. A plain // or
      /* is not documentation - treating one as such would attach
      commented-out code to whatever follows it.

      Where a symbol has several declarations this renders the NEAREST.
      Hover is a glance; dm_definition_at is what returns the whole chain.

  dm_definition_at(ws, file, line, character, encoding, &json)   NEW in 0.6
      Where the symbol at a position is declared, as UTF-8 JSON. YOU FREE IT
      with dm_free. Line and character are ZERO-BASED.

      ** IT RETURNS A LIST, AND SEVERAL RESULTS IS NORMAL **
      DM declares one symbol in several places routinely: a type is reopened
      across files, and a proc has an override chain. We report all of them
      instead of picking one, because the pick would be arbitrary and the
      rest are exactly what a reader wants in an override-heavy codebase.

      Order is NEAREST FIRST - the nearest override is what a call actually
      reaches - so if your editor insists on a single destination, take the
      first and offer the rest rather than dropping them.

      An empty array means nothing resolved. That is normal and not an
      error: locals, parameters and macros are not in the object tree.

      Each entry has the same two ranges as dm_document_symbols. Navigate
      with the sel* range so the caret lands on the name.

      "file" is an absolute path, and it is often NOT the file you asked
      about - that is the point.

      ** COST ** Same as dm_complete_at: the first call after an edit
      rebuilds the object tree. Debounce it.

  dm_classification_count(spans)     -> N, or -1 if the handle is invalid
  dm_classification_data(spans)      -> pointer to 3*N int32s, or NULL
  dm_classification_free(spans)      -> release it

      The data block is (offset, length, kind) repeated N times, contiguous.
      memcpy it if you want, it is plain int32s. Valid until you call free.

  dm_query_json(ws, request, &json)                            NEW in 0.11
      A bulk question about the object tree, as UTF-8 JSON in and out. YOU
      FREE IT with dm_free. The full shapes are in abi/dm_core.h and frozen
      in abi/schema/; this is what they are for.

      THIS IS WHAT YOUR TREE PANEL RUNS ON. The position-shaped calls answer
      about a caret; these answer about a PATH, and return a lot at once.

        {"query":"objectTree","path":"/obj","depth":1}
            one node and its children. depth 1 is a node the user just
            expanded, depth 0 is a single-row refresh
        {"query":"subtypesOf","path":"/obj","limit":500}
            everything beneath a path, flat, in tree order
        {"query":"members","path":"/mob","inherited":true}
            a type's vars and procs, with inheritance already resolved -
            each one says which type it came from

      Two fields exist so you do not have to make a second call or a wrong
      guess:

        "childCount" is how many children EXIST, which is not the length of
        "children" when depth cut the response short. Draw your expander
        arrow from this. Without it, every collapsed row costs a round trip.

        "truncated" says the limit cut the list. A list exactly as long as
        the limit looks identical to one that was cut, so do not infer it
        from the count - if you do, your picker will claim a type has 500
        subtypes when it has 4,000.

      "parentType" is where a type INHERITS from, which is not always its
      path parent: /mob is a child of the root by path and inherits from
      /atom/movable. Draw the tree by path and show parentType separately,
      or your panel will describe a different program from the one that runs.

      Unknown members in a request are ignored, so a client written against
      a later schema still gets an answer from an older library. An unknown
      query name or a malformed request is DM_ERR_INVALID_ARG; a path that
      is not in the tree is DM_ERR_NOT_FOUND. An empty array with DM_OK is
      an answer - a type with no subtypes.

      ** COST ** Same as dm_complete_at: the first call after an edit
      rebuilds the object tree. Debounce it, and prefer one deep query to
      many shallow ones while typing.

  dm_workspace_close(ws)
      Done. Safe to call on an already-closed handle.


--------------------------------------------------------------------------------
 5. ENCODING - READ THIS ONE
--------------------------------------------------------------------------------
  Every call that deals in offsets takes an encoding. There is no default and
  we will not guess.

    DM_ENCODING_UTF16   offsets count UTF-16 code units
    DM_ENCODING_UTF8    offsets count UTF-8 bytes

  WHICH DO I WANT?

    Qt / QString              -> DM_ENCODING_UTF16
    C# / .NET string          -> DM_ENCODING_UTF16
    Java / JavaScript string  -> DM_ENCODING_UTF16
    std::string / raw bytes   -> DM_ENCODING_UTF8
    Rust String / &str        -> DM_ENCODING_UTF8
    Python 3 str              -> neither is exact; use UTF-8 and index bytes

  ** WHY THIS WILL BITE YOU **

  For pure ASCII the two are IDENTICAL. So if you pick the wrong one,
  everything works. Your tests pass. You ship it.

  Then a user types a comment with an accented character, or an emoji, or CJK
  text in a string literal - and every colour on that line after it shifts by
  one to three characters. It will look like a bug in our lexer. It is not.

  Pick the right one now. If you are unsure, write one test with a non-ASCII
  character in it and check the colours still line up.


  LINE ENDINGS - THE OTHER TEXT TRAP, AND THIS ONE IS YOUR PROBLEM NOT OURS
  --------------------------------------------------------------------------
  DM files are usually CRLF on Windows. Editor frameworks normalise hard:
  Qt's QTextDocument and QPlainTextEdit::toPlainText() always hand you \n
  whatever was on disk, and QIODevice::Text translates on read.

  FOR US THAT IS HARMLESS, as long as you push your buffer via dm_set_buffer.
  We then analyse exactly what your editor displays, and every position we
  return is line/column, which a \r cannot shift. SourceText treats \r\n,
  bare \n and a lone \r as terminators, and \r never appears inside token
  text.

  FOR YOU IT IS NOT HARMLESS, for three reasons:

    1. Reading with translation and writing without it rewrites EVERY LINE
       on save. Whole-file diffs, and git blame is dead for the rest of the
       team.
    2. DM's {" multiline "} strings carry their newlines as CONTENT.
       Converting endings inside one changes program data, not formatting.
    3. Offsets computed from your buffer will not match offsets into the
       file on disk.

  DO THE ROUND TRIP YOURSELF. No editor framework does it for you:

    - open with QFile::ReadOnly WITHOUT QIODevice::Text, so bytes arrive raw
    - sniff the dominant ending, store it per document
    - normalise to LF internally - correct, and what this library wants
    - re-apply the stored ending on save
    - put "*.dm text" in the game repo's .gitattributes so git agrees


--------------------------------------------------------------------------------
 6. COLOURS
--------------------------------------------------------------------------------
  `kind` is one of these. Values are a permanent contract and are never reused.

     0  DM_CLASS_NONE                     default foreground
     1  DM_CLASS_COMMENT                  // and /* */
     2  DM_CLASS_KEYWORD                  var, if, for, src, return, ...
     3  DM_CLASS_IDENTIFIER               everything else that is a name
     4  DM_CLASS_NUMBER                   42, 3.5, 0x1F, 1e10
     5  DM_CLASS_STRING                   "..." and {"..."} incl. the quotes
     6  DM_CLASS_INTERPOLATION_DELIMITER  the [ and ] inside a string
     7  DM_CLASS_RESOURCE                 'icons/mob.dmi'
     8  DM_CLASS_OPERATOR                 + - * / = < > etc
     9  DM_CLASS_PUNCTUATION              ( ) [ ] { } , ;
    10  DM_CLASS_PREPROCESSOR             #define, #include, #if ...
    11  DM_CLASS_ERROR                    we could not understand this

    SEMANTIC - produced now:
    12  DM_CLASS_TYPE_NAME                a path segment naming a real type
    13  DM_CLASS_PROC_NAME                a name followed by (
    14  DM_CLASS_VAR_NAME                 a member read with no call parens
    15  DM_CLASS_MACRO_NAME               a name the project #defines

  ABOUT 12-15
    These only ever REFINE a span the lexical pass already produced. No span
    is added, removed or moved, so if you ignore them you get exactly the
    output you got before - which is why mapping them was safe to do early.

    They are deliberately conservative. A wrong colour reads as a bug in us;
    a missing one reads as "not implemented yet", so we under-claim. A bare
    "mob" stays an identifier, because it is more often a variable than the
    type.

    12 needs the object tree, and CLASSIFICATION WILL NOT BUILD ONE - a
    whole-project walk on your paint path would be a bad trade. So type
    names stay plain identifiers until something else builds a tree
    (dm_complete_at, dm_document_symbols), and light up from then on. If you
    want them immediately, call dm_complete_at once after opening.

  Handle unknown values by falling back to the default colour. That way a
  library update cannot break your renderer.

  NOTES ON SPECIFIC KINDS

    INTERPOLATION_DELIMITER is separate from STRING so that "[src.name]" reads
    as string, bracket, code, bracket, string. Colour the brackets like an
    operator and the hole reads as code, which is what people expect.

    Spans do NOT cover whitespace. The gaps between spans are whitespace and
    layout - paint them with your background.

    Touching spans of the same kind are already merged. A three-token string
    comes back as one span, not three.


--------------------------------------------------------------------------------
 7. ERRORS
--------------------------------------------------------------------------------
  Every function that can fail returns dm_status. DM_OK is 0.

    DM_OK                    0
    DM_ERR_INVALID_ARG       1   you passed a null or nonsense argument
    DM_ERR_INVALID_HANDLE    2   handle is closed, freed, or garbage
    DM_ERR_NOT_FOUND         3   file does not exist and has no buffer
    DM_ERR_OUT_OF_MEMORY     4
    DM_ERR_INTERNAL          5   our bug. please report with the message.

  char *msg = dm_last_error();   // may be NULL. YOU FREE IT with dm_free.

  dm_last_error is per-thread and reflects the last failing call on that
  thread.

  Out-parameters are always cleared before we do any work, so reading them
  after an ignored error gives you NULL rather than uninitialised stack.

  WE NEVER THROW ACROSS THE BOUNDARY. An exception escaping into your process
  would kill your IDE, so every entry point converts failures into a status
  code. If we ever crash your process, that is a bug worth reporting loudly.


--------------------------------------------------------------------------------
 8. THREADING
--------------------------------------------------------------------------------
  Current contract: ONE WORKSPACE IS USED FROM ONE THREAD AT A TIME.

  This is not enforced, and violating it will corrupt state rather than fail
  cleanly. If you analyse on a worker thread, either keep all calls on that
  thread or hold a mutex.

  Different workspaces on different threads is fine.

  Background analysis with callbacks is a later feature. Ask if you need it
  sooner and we will move it up.


--------------------------------------------------------------------------------
 9. WHO FREES WHAT
--------------------------------------------------------------------------------
  Anything we hand you, you release. Nothing we hand you points into memory we
  might move.

    char *          from dm_last_error, dm_workspace_root  -> dm_free()
    dm_classification                                      -> dm_classification_free()
    dm_workspace                                           -> dm_workspace_close()

  Anything you hand us is copied before the call returns. Free your own copy
  whenever you like.

  USING A FREED HANDLE IS SAFE-ISH BY DESIGN. A handle is an opaque id that is
  never reused, so a stale one returns DM_ERR_INVALID_HANDLE (or -1 / NULL)
  rather than silently resolving to whatever was opened next. Do not rely on
  this, but it means a use-after-free in your code is a clean error you can
  find, not memory corruption you cannot.

  Treat the value as opaque. It is not a pointer, not an index, and carries no
  structure worth reading - it changed shape once already, when the previous
  encoding turned out to need 64-bit pointers and silently did not have them on
  win-x86.

  Closing twice is a no-op, not a crash.


--------------------------------------------------------------------------------
 10. PERFORMANCE
--------------------------------------------------------------------------------
  What actually happens when you call dm_classify_range:

    - if the buffer changed since last time, the WHOLE FILE is re-lexed
    - the result is cached on the document
    - only your requested line range is packed and returned

  Why the whole file: a {" multiline string "} or a nested /* comment */ can
  open thousands of lines above your visible range, and it decides whether
  line 900 is code or text. Lexing just the visible range gives wrong colours.

  Practically: cost is paid once per edit, not once per scroll. Scrolling a
  large file re-uses the cached lex and is cheap.

  Do not call dm_set_buffer with identical text on every paint. That throws
  away the cache and re-lexes. Call it when the text actually changes.

  WHAT AN EDIT COSTS NOW, WHICH IS THE NUMBER BEHIND EVERY "DEBOUNCE IT"
  ABOVE. The calls that need the object tree - dm_complete_at,
  dm_definition_at, dm_hover_at, dm_workspace_symbols, dm_query_json - used
  to rebuild the entire project on the first call after any edit. They no
  longer do. A file is re-read, re-walked and re-parsed only when its text or
  the macro state reaching it actually changed, which after one keystroke is
  one file:

    100 files    (a real game)        131 ms  ->   10 ms
    7,161 files  (/tg/station)         13.7 s  ->  909 ms

  Both figures are one keystroke, warm, Release, and both were verified
  against a build of the same text with every cache off - 335,519
  declarations identical on the large one. Editing a #define is the
  expensive case by design: everything downstream of it genuinely changed,
  so that one edit costs a full rebuild and the next is fast again.

  What is still whole-project is the final merge into the object tree, which
  is most of what remains on the large figure. So: still debounce, but the
  budget you are debouncing against is tens of milliseconds on a normal
  project rather than a rebuild you can see.

  You need do nothing to get this. We revalidate each file against its
  last-write time and length rather than trusting the cache, chosen so that a
  git checkout under your running IDE is still seen - no API call, nothing to
  remember, and no staleness if a build script rewrites files behind you.

  Incremental re-lexing WITHIN a single edited file (only the changed region)
  is still not done. Say something if you hit a file where re-lexing the whole
  buffer per keystroke is too slow, ideally with the file size.

 11. TROUBLESHOOTING
--------------------------------------------------------------------------------
  Build fails copying dm_core.dll, or the DLL vanishes after publishing
      Windows Defender can quarantine a freshly built NativeAOT binary as a
      false positive. Seen on this project: the publish reports success, then
      dm_core.dll is gone from both publish/ and native/, and CMake fails on
      the copy step with a wall of MSB3073 text that says nothing about
      antivirus. Check with:
        Get-MpThreatDetection | Select-Object -Last 1 | Format-List Resources
      If your own build output is listed, add a Defender exclusion for the
      repo directory. This will hit CI on Windows runners too.

  "unresolved external symbol dm_..."
      You are not linking dm_core.lib, or you are linking a stale one.
      On Windows you link the .lib and ship the .dll. Both.

  Program starts and immediately exits, code 0xc0000135
      dm_core.dll is not next to your executable.

  dm_workspace_open returns 3 (NOT_FOUND)
      The .dme path is wrong. Check dm_last_error for the resolved path we
      actually tried.

  Everything returns 2 (INVALID_HANDLE)
      You are passing a handle that was closed, or never initialised. Note we
      clear out-params on failure, so an ignored error leaves you holding NULL.

  Colours are right on ASCII lines and wrong after accented / CJK characters
      Wrong encoding. See section 5.

  Colours are right, but shifted by a line
      Line numbers are ZERO-based here. Editors often display 1-based.

  A whole file colours as one giant string
      An unterminated {" ... "} somewhere above. That is correct behaviour -
      it is also what the DM compiler sees. Check for a stray {" .

  Whole file colours as a comment
      Same thing with /* and no */. DM nests block comments, so an extra /*
      inside a comment needs its own */.

 12. HOW TO CHECK OUR OUTPUT
--------------------------------------------------------------------------------
  If you think we are classifying something wrong, check with the CLI before
  digging into your own code. It uses the exact same code path as the ABI.

    dotnet run --project src/Dm.Cli -- classify <file.dm>
        renders the file with colours in your terminal

    dotnet run --project src/Dm.Cli -- classify <file.dm> --spans
        the raw span table, with BOTH utf16 and utf8 offsets side by side.
        very useful for confirming an encoding problem.

    dotnet run --project src/Dm.Cli -- dump-tokens <file.dm>
        the raw token stream, if you want to see why a span came out that way

    dotnet run --project src/Dm.Cli -- scan <file-or-directory>
        reports anything the lexer did not recognise across a whole codebase

    dotnet run --project src/Dm.Cli -- outline <file-or-directory>
        the declarations we found in a file

    dotnet run --project src/Dm.Cli -- symbols <file>
        the document outline: kind, name, detail, and the line:col of each
        name. this is the exact shape the ABI call will hand you, so you can
        design your outline pane against it today
        --utf8   columns in UTF-8 bytes, to check your encoding choice

    dotnet run --project src/Dm.Cli -- query <dme> --path /obj --depth 2
        the same answers dm_query_json gives, rendered as a tree
        --subtypes <path> / --members <path> for the other two queries

  WHEN A TYPE OR MEMBER IS MISSING AND YOU WANT TO KNOW WHY, these three walk
  the same pipeline we do, one stage at a time. Work down the list - the first
  one that looks wrong is the stage that broke.

    dotnet run --project src/Dm.Cli -- includes <dme>
        every file the project compiles, IN COMPILE ORDER. if a file is not
        here, nothing in it exists to us
        --tree      show the include nesting
        --orphans   .dm files on disk the .dme never reaches
    dotnet run --project src/Dm.Cli -- preprocess <dme>
        the whole project expanded, in compile order
        --macros    which macros produced how many tokens
        --dump      every token, showing where it traces back to
    dotnet run --project src/Dm.Cli -- tree <dme>
        the object tree, built in compile order
        --under <path>     what is declared beneath a type
        --members <path>   one type's members, inherited included
        --problems         parse diagnostics grouped by message

    dotnet run --project src/Dm.Cli -- complete <dme> <file> <line> <col>
    dotnet run --project src/Dm.Cli -- definition <dme> <file> <line> <col>
    dotnet run --project src/Dm.Cli -- hover <dme> <file> <line> <col>
    dotnet run --project src/Dm.Cli -- wsymbols <dme> <query>
        the same answers dm_complete_at, dm_definition_at, dm_hover_at and
        dm_workspace_symbols give you.
        ** LINES AND COLUMNS ARE 1-BASED IN THE CLI AND 0-BASED IN THE ABI **
        so add one when reproducing what your editor asked for.

    Every command that reads a .dme takes -DNAME as well, so you can
    reproduce a query with the same defines you pass to dm_set_defines.

  RULE OF THUMB: if the CLI reproduces the problem, it is ours - report it.
  If the CLI looks right and your editor does not, it is in your integration.
