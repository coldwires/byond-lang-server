FOR THE IDE DEVS - WHAT YOU CAN CALL TODAY
--------------------------------------------------------------------------------
  Highlighting is the shortest path in, and it is the sequence below.
  Completion, definition, hover, workspace symbols and the document outline
  are all callable too - see INTEGRATION.txt for their arguments and the
  ownership rules.

  dm_workspace_open(dme_path, &ws)
  dm_set_buffer(ws, "file.dm", utf8_text, byte_length)   // unsaved text
  dm_classify_range(ws, "file.dm", first_line, last_line, encoding, &spans)
  dm_classification_count(spans)                          // N
  dm_classification_data(spans)                           // 3*N int32s
  dm_classification_free(spans)

  Data is offset,length,kind triples in one contiguous block - memcpy it.
  Pass DM_ENCODING_UTF16 if you hold a QString or a C# string.
  Pass DM_ENCODING_UTF8 if you hold raw bytes.
  Getting that wrong LOOKS FINE until someone types a non-ASCII character.

  Kinds are #defined in abi/dm_core.h. Values 12-15 are SEMANTIC and are
  produced now: type name, proc name, var name, macro name. They only refine
  a span the lexical pass already made - nothing is added or moved - so
  ignoring them gives you the old output exactly.
  Type names need the object tree, and classification will NOT build one on
  your paint path; they light up once something else has (completion,
  symbols).

  TRY IT
    dotnet run --project src\Dm.Cli -- preprocess <file.dme>
        the whole project expanded, in compile order
        --macros    which macros produced how many tokens
        --dump      every token, showing where it traces back to
    dotnet run --project src\Dm.Cli -- includes <file.dme>
        every file the project compiles, in COMPILE ORDER
        --tree      show nesting
        --orphans   list .dm files on disk that the .dme never reaches
    dotnet run --project src\Dm.Cli -- classify <file.dm>
        renders the file with syntax colours in your terminal
    dotnet run --project src\Dm.Cli -- classify <file.dm> --spans
        the span table, with utf16 and utf8 offsets side by side
    dotnet run --project src\Dm.Cli -- outline <file-or-directory>
        the declaration structure: types, vars, proc signatures
    dotnet run --project src\Dm.Cli -- tree <file.dme>
        the object tree, built in compile order
        --under <path>     list what is declared beneath a type
        --members <path>   one type's members, inherited ones included
    dotnet run --project src\Dm.Cli -- symbols <file>
        the document outline exactly as the ABI will return it
        --params    include proc parameters
        --utf8      columns in UTF-8 bytes instead of UTF-16 units
    dotnet run --project src\Dm.Cli -- complete <dme> <file> <line> <col>
        what can be typed there. lines and columns are 1-based in the CLI,
        0-based across the ABI
    dotnet run --project src\Dm.Cli -- definition <dme> <file> <line> <col>
        every declaration of that symbol, nearest first
    dotnet run --project src\Dm.Cli -- hover <dme> <file> <line> <col>
        the tooltip: resolved path, declaration as written, doc comment
    dotnet run --project src\Dm.Cli -- wsymbols <dme> <query>
        search the project by name, ranked
        --limit <n>        how many hits (default 200)
    dotnet run --project src\Dm.Cli -- query <file.dme>
        browse the tree the way an IDE panel does
        --path <path>      the node to browse (default /)
        --depth <n>        levels of children (default 1)
        --subtypes <path>  flat list of everything beneath a path
        --members <path>   a type's vars and procs, inherited included
    dotnet run --project src\Dm.Cli -- dump-tokens <file.dm>
    dotnet run --project src\Dm.Cli -- scan <file-or-directory>

    Every command that reads a .dme also takes -DNAME, -DNAME=value and
    -DFN(x)=body. Pass what the build passes or you are analysing a
    different program.

    "scan" is the important one. It reports anything the lexer didn't
    understand across a whole codebase. The DM reference doesn't list every
    operator or edge case, so real code is the only reliable source.

PREPROCESSED PARSING - NOW THE DEFAULT
--------------------------------------------------------------------------------
  dmc tree <dme>          the expanded stream (default)
  dmc tree <dme> --raw    each file's own text, macros stay opaque

  ON mlaas IT IS EXACT: 1493/1493 vars, 1153/1153 procs vs dm.exe -o, nothing
  invented, both paths. That is the number that matters - see BENCH - mlaas.

  On tgstation:
                              raw        preprocessed
    var recall              94.37%          99.99%   (26 missing)
    proc recall             96.50%          99.92%   (55 missing)
    macro-shaped phantoms      246               9
    files with problems        229             102
    wall clock                 37s             15s

  The half it was built for WORKS. GLOBAL_VAR(my_thing) now lands on
  /datum/controller/global_vars, VAR_PRIVATE/hidden lands on /atom, and the
  phantom types nearly all disappear. Vars go up to match.

  Parse problems are now BELOW the raw path. Two causes found and fixed, both
  by reading the actual diagnostics (dmc tree --problems) instead of reasoning
  about the count:

    - the conditional-":" whitespace probe read a REPOSITIONED span.
      ExpressionParser answered the spacing rule by looking at the character
      before the token. Reposition that onto a macro invocation and the
      character before the INVOCATION decides the parse of the text inside
      it. 5,064 bogus "expected ':'" plus 6,044 "expected an expression"
      behind it. TokenSource.HasWhitespaceBefore now captures the fact where
      the token really lives. Problems went 1,630 -> 102.
    - "#pragma syntax" did not survive preprocessing. Directives are
      consumed, so the statement parser never saw "C for" / "C switch" and
      parsed those bodies under the default grammar. FIXED: IncludeGraph
      puts syntax/push/pop back into the stream and the parser's existing
      directive handling applies them. Everything else stays consumed.
      On a fixture dm.exe compiles with 0 errors, we went from 10 bogus
      diagnostics to none. Barely matters on tgstation - 31 pragmas, no
      syntax ones - but a file that uses it was unreadable to us.

  THIRD CAUSE - INDENTATION ACROSS A SKIPPED #if. Found on mlaas, not here.
  A skipped region takes its Indent tokens with it while the matching Dedents
  survive in live code, so the stream pops levels it never pushed. Everything
  after reads one level too shallow and members land on the ROOT. It still
  parses - zero diagnostics - which is why the count never showed it.
  IncludeGraph now tracks the file's own depth across skipped regions and
  emits the difference before each surviving token. Worth 128 procs and 113
  vars on mlaas: the entire gap.

  Vars now beat raw outright. Procs are still 0.46 points behind ON TGSTATION
  ONLY - mlaas is exact both ways.

  THE ORACLE IS REPRODUCIBLE, AND dm.exe IS NOT IFFY HERE:
    dm.exe -o -DCBT tgstation.dme
  exits 0 with zero errors and produces a file BYTE-IDENTICAL to the
  objtree.xml we had been diffing against - same 54,626,955 bytes. So the
  baseline is trustworthy, it is already a -DCBT build, and it can be
  regenerated on demand. Any remaining disagreement is OURS.

  -D DID NOT CLOSE THE GAP, and the guess that it would was wrong. Passing
  -DCBT grows our tree by ~940 var declaration SITES and adds not one new
  owner/name pair; recall is identical to the digit. CBT mostly steers
  MAP_SWITCH, which picks between operands rather than declaring different
  things. -D is still necessary - a build whose flags we ignore is a
  different program - it is just not what this gap was made of.

  WHAT THE GAP IS MADE OF:
    missing   /datum/controller/subsystem/*  (shuttle 57, mapping 44, air 41,
              ticker 35, job 28) - DIAGNOSED, see below
    invented  /particles/*  (16-17 each across many) and
              /datum/admin_verb/cmd_admin_areatest 21 - not investigated

  SUBSYSTEM_DEF - WAS A DECLARATION PARSER GAP. FIXED.
    The macro expands through \ continuations into a run of declarations on
    ONE logical line, ending with a bare type path that owns the indented
    block written under the invocation. Reduced, no macros needed:

      var/glair;/datum/sub/air
        var/thing = 1

    dm.exe declares the var AND the type, with thing under the type. We
    declared only the var: the ";" ended the name list, then the parser
    consumed to end of line and swallowed the indented block with it.

    Fixed by suppressing both when a ";" hands the rest of the line to a new
    declaration. "var/a; b" still shares one var/, and a trailing ";" still
    ends the line - dm.exe accepts all three and they take different paths.

    tgstation: vars 95.42 -> 96.00%, procs 96.04 -> 97.90%. The subsystem
    cluster is gone from the top misses; what is left is scattered at 5-9.

    HOW IT WAS NEARLY MISDIAGNOSED: three printf fixtures "reproduced" it
    with a literal

    backslash name-escape. They failed for an unrelated reason and pointed
    at brace blocks, which are fine. Only a heredoc with real continuations
    isolated it. Same class as the grep bugs: THE HARNESS WAS WRONG AND GAVE
    A CONFIDENT WRONG ANSWER. Write fixtures with a heredoc, and check the
    file with cat -A before trusting a negative result.

  Re-run the table after each attempt. It has now disagreed with the obvious
  expectation three times - once by improving the thing that looked broken,
  once by not moving after a fix that removed 11,000 diagnostics, and once by
  hiding a whole-project defect behind a metric that shifted under a point.

  Two real preprocessor bugs fell out of pointing it at 1.5M lines, both
  pre-existing and both now fixed:
    - MacroExpander.RawText sliced the original text between the first and
      last token of a run. A body naming a parameter twice, or the ###
      repeat operator, makes that run go backwards and it threw.
    - reported positions inside one expansion are not monotonic. a body
      token reports at the invocation while an argument keeps the caller's
      position, so "#define X(a) a + a" yields argument, body, argument -
      and the parser builds node spans with FromBounds across the run.

THE ORACLE'S BLIND SPOT - dm.exe -o DOES NOT REPORT EVERYTHING
--------------------------------------------------------------------------------
  -o omits WHOLE BUILTIN BRANCHES. A /particles, /sound or /image subtype is
  absent from the dump entirely, even when it declares brand new vars:

    /particles/withvar
      var/mine = 1        <- absent from -o
    /datum/plain
      var/mine = 1        <- reported

  It is NOT about builtin members. /obj/box overriding the builtin "name" and
  /mob/guy overriding the builtin Login() are both reported fine. The branch
  is what decides.

  The reference has ZERO entries under /particles, /sound and /image. We have
  474, correctly. So of 1,168 "invented" vars, 477 sit in this blind spot and
  are RIGHT. Honest remainder: 691 vars, 1,096 procs.

  DO NOT CHASE "invented" TO ZERO - that would mean deleting types dm.exe
  agrees exist. Recall is unaffected (it is measured against the reference),
  but any precision number must exclude these branches or it is measuring the
  oracle instead of us.

VERIFIED AGAINST dm.exe 516.1666
--------------------------------------------------------------------------------
  Tested by compiling cases where the two candidate behaviours give different
  compiler output. Not guessed, not read off a doc page.

    block comments DO nest
    "//" inside a block comment hides both /* and */ until end of line
    quotes do NOT protect a */ inside a block comment
    including the same file twice is silently ignored, not an error
    #include accepts forward slashes as well as backslashes
    /mob already has built-in x, y, z - declaring var/x on a mob is an error
    indentation depth is tab count, falling back to space count when there are
      no tabs. against a sibling at one tab, dm.exe accepts " \t", "\t " and
      " " as the same level but rejects four spaces. NOT a prefix comparison.
    #warn / #error bodies are free text, not tokens
    a conditional's ":" is member access only when tight against a bare
      identifier. "x?y:z" is an error, "x?\"a\":\"b\"" and "x?f():g()" are not
    1#INF and 1#IND are number literals
    #if rejects undefined identifiers instead of treating them as 0
    in binds looser than assignment, % truncates and %% does not, ..() with
      empty parens forwards the current arguments, and names may contain \
      escapes. full table in PLAN.md 8, runnable proofs in
      docs/dm-language-notes.md
    DM has NO local type inference. "var/x = new /obj/item" then "x.hp" is
      "undefined var" - the right member of the type on the line above.
      only a WRITTEN type is checked. not new, not as, not assignment from
      a typed var. we infer anyway; see WHERE WE DISAGREE below.
    "." on an untyped var rejects EVERY member. ":" on an untyped var
      accepts any name that exists on some type somewhere. untyped is not
      unchecked, and the two need different lists.
    "mk().elsewhere" compiles but "var/x = mk()" then "x.elsewhere" does
      not. same unknowable type; a variable in the way flips the answer.
    dm.exe -DNAME / -DNAME=value / -DFN(x)=... all work. bare -DNAME
      defines it EMPTY, not 1.
    a var's declared type is resolved AT THE USE SITE. "mob/var/clothing/slot"
      with no /clothing anywhere compiles with 0 errors and -o lists slot as a
      real var. the first line that reads or writes it fails with "slot:
      undefined type: /clothing", ON THE USE LINE. clean build, broken var.
    separators in a var declaration create NO types. mob/var/clothing/feet is
      one var "feet" on /mob and nothing else - /clothing, /clothing/feet and
      /mob/clothing are all "undefined type path". checked with -o, not
      guessed from a clean compile.
    leading "." follows the PATH ancestry, not parent_type. it validates the
      WHOLE relative path and backtracks, and the nearest ancestor where all
      of it resolves wins. see PLAN 4a - the old "first hit wins" wording
      would have been built against the inheritance chain, which is wrong.

  HOW WE TEST - "IT COMPILED" IS NOT A RESULT
    A construct being accepted only means the parser allowed it. Three things
    in docs/dm-language-notes.md compile with 0 errors and do not mean what
    they look like. So:
      - ask whether the thing EXISTS. reference the type as a path, assign to
        the var, call the proc.
      - read the tree with -o instead of inferring it.
      - always include a negative control. a probe that cannot fail proves
        nothing.
      - watch for probes that collide. "name" is a builtin on /mob, x/y/z are
        builtins on /turf and /mob - a bad probe name reports a duplicate
        definition that has nothing to do with your question.
      - check the error's LINE NUMBER. it is evidence.

  Nothing about the language is untested now. The last guess - whether a brace
  block can hold indentation-structured sub-blocks - was answered by compiling
  one: YES, and the braced and indented forms produce an IDENTICAL -o tree.

WHERE WE DISAGREE WITH dm.exe - ON PURPOSE, EXACTLY ONCE
--------------------------------------------------------------------------------
  Completion infers a type for an untyped local from "new", "as" and
  assignment. The compiler does not, and will reject the members we offer.

  We do it because "var/x = new /obj/item" is nearly always a half-written
  declaration, and those are the members the author is reaching for.

  The cost: a user can accept our completion and get code that does not
  build. That is written down for integrators in INTEGRATION.txt section 4,
  and the matching M11 warning ("x is untyped, `.` cannot compile here") is
  on the list. Nothing else in the library pretends the var has a type -
  the object tree and the diagnostics both agree with dm.exe.

DM0300 - THE FIRST WARNING, SHIPPED EARLY   [DONE]
--------------------------------------------------------------------------------
  A proc block indented one level too far, into a var block, declares NOTHING.
  dm.exe takes it with 0 errors and 0 warnings and drops everything under it -
  not a proc, not a var, absent from vars, and calling it is a runtime
  "undefined proc or verb". Runnable proof: docs/dm-language-notes.md 18.

    /datum/swallowed
      var
        kept = "this one survives"
        proc
          vanished()          <- does not exist at runtime

  We now declare nothing there either, which is what the compiler does, and
  warn on the header, which is what the compiler does not. Nothing else in a
  DM toolchain reports it. It was found in a shipped game where four mission
  procs were declared this way and one is called from another file.

  The warning arrives in dm_document_symbols with the syntax errors, so
  clients need no new call. DM03xx is the range for this class: code that
  compiles clean and does not mean what it looks like. An ERROR would be
  wrong - the file compiles.

  madridspy is now 507/507 procs and 1231/1231 vars against dm.exe -o. The one
  remaining extra is /icon ChangeOpacity, which is the -o blind spot below and
  is ours being right. tgstation has no occurrences at all.

INJECTED DEFINES - dm.exe -D   [DONE for the core and the CLI]
--------------------------------------------------------------------------------
  A project built with "dm.exe -DDEBUG game.dme" compiles a DIFFERENT
  program from the one we analyse, because we never see the -D. Anything
  behind "#ifdef DEBUG" is invisible to us, or visible when it should not be.

    dmc tree game.dme -DCBT -DFLAVOUR=3 -DFN(x)=((x)*2)

  Accepted by every command that reads a .dme, in both spellings (-DNAME and
  -D NAME). A bare -DNAME defines it EMPTY, not 1, matching the compiler.
  IncludeOptions.Defines is the library entry point.

  THROUGH THE ABI TOO, as of 0.5:
    dm_set_defines(ws, defines, count)
  Set it straight after opening - the tree is lazy, so it still applies to
  the first query, and flags can change later without reopening.

  For the IDE devs: pass the same -D set to us and to dm.exe, or the
  highlighting and the build will disagree. Pre/post-compile hooks are yours
  to own - we have no build step to hang them off.

WARNING NAMES - A SHARED VOCABULARY, AND IT BINDS M11
--------------------------------------------------------------------------------
  The names -ignore/-warn/-error take are THE SAME IDENTIFIERS as
  #pragma ignore|warn|error. The compiler prints the name inline:

    lint.dm:2:warning (init_proc): stuff: var will be initialized in a hidden
    lint.dm:3:warning (frequent_call): New: this proc will be called very ...

  So you can enumerate them off any build log. The reference does not list them.

  Two ship OFF BY DEFAULT and are meant for linting:
    init_proc       a var whose initializer is NOT a compile-time constant,
                    so it needs a hidden per-instance init proc
    frequent_call   New() or Del() overridden

    dm.exe -DCBT -warn init_proc,frequent_call tgstation.dme

  BOTH FIRE ON THE SAME SET, and its shape is easy to get wrong:
    /datum /atom /turf  ... the EXACT types                        WARN
    /turf/sub, /turf/a/b/c ... any turf subtype at any depth       WARN
    /datum/sub, /atom/sub                                          silent
    /atom/movable /obj /obj/sub /mob /area /client /image          silent

  So it is the three exact types PLUS the whole /turf subtree - the union,
  not either rule alone. Inheritance is not the rule: /obj descends from
  /atom and is silent. The reference names "/turf or /atom or /datum", which
  is right about the exact types and silent about the turf subtree.

  Matches the intent: a var or New() on /datum or /atom EXACTLY is inherited
  by every object in the game, and the map creates turfs per tile for every
  turf subtype. Everything else is made on demand.

  PRACTICAL CONSEQUENCE: neither lint fires on /obj/item or /mob/living,
  which is where a big codebase's per-instance cost actually is. Much weaker
  as a whole-codebase audit than the names suggest - an argument for doing
  our own at M11 rather than shelling out to dm.exe.

  init_proc is about CONSTANT vs NOT, not about lists:
    warns:  = list(1,2,3)  = list()  = new /obj  = newlist(/obj)
    silent: = 5  = "text"  = 1+2  = /obj  = null  no initializer  const
  frequent_call is New and Del only - proc/whatever() and Enter() are silent.

  THE PRAGMA BEATS THE FLAG, both ways:
    -warn X   + #pragma ignore X  -> silent
    -ignore X + #pragma warn X    -> warns
  So the flag sets the starting level and the pragma overrides from there.
  push/pop scopes it. -error and #pragma error both produce a REAL error,
  printed as "error (name):" not "warning (name):".

  WHAT THIS MEANS FOR US: a project can already write "#pragma ignore
  init_proc" to silence a diagnostic, with push/pop to scope it. If our
  diagnostics live in a private DM0200 ID space, none of that reaches them and
  we will report things the author explicitly silenced - which reads as our
  bug, not as their setting. So where we report the same thing the compiler
  names, USE THE COMPILER'S NAME. Private IDs are for what dm.exe has no name
  for, like the discarded-proc warning.

  Both lints are also worth implementing ourselves. They are off by default,
  so most projects have never seen them, and we can show them continuously
  instead of once per build.

LINE ENDINGS (for the Qt dev)
--------------------------------------------------------------------------------
  Qt normalises CRLF to LF. QPlainTextEdit::toPlainText() always returns \n,
  and QIODevice::Text translates on read. That is FINE for us as long as the
  client pushes its buffer via dm_set_buffer - we then analyse exactly what the
  editor displays, and all our positions are line/column, which \r cannot shift.

  It is NOT fine for him, for three reasons:
    1. Reading with translation and writing without it silently rewrites every
       line on save. Whole-file diffs, dead git blame.
    2. DM's {" multiline "} strings carry their newlines as CONTENT. Converting
       endings inside one changes program data, not just formatting.
    3. Offsets computed from his buffer won't match disk offsets.

  Fix - do what every editor does, Qt won't do it for you:
    - open with QFile::ReadOnly WITHOUT QIODevice::Text so bytes arrive raw
    - sniff the dominant ending, store it per document
    - normalise to LF internally (correct, and what our library wants)
    - re-apply the stored ending on save
    - put "*.dm text" in the game repo's .gitattributes so git normalises too

HOW IT WORKS
--------------------------------------------------------------------------------
  Pipeline, in order:
    SourceText     - file contents, disk + unsaved editor buffers on top
    Lexer          - text -> tokens, emits Indent/Dedent (DM uses indentation)
    Preprocessor   - expands #define, follows #include, keeps a source map
    Parser         - tokens -> AST per file, recovers from broken code
    TypeTreeBuilder- merges all files into one object tree, adds builtins
    Binder         - resolves names and types, answers questions about a cursor
    Services       - completion / symbols / hover / definition / diagnostics

  Two ways to consume it:
    In-process  - C# IDE references Dm.Core, gets real objects (Roslyn style).
    C ABI       - everyone else calls dm_core.dll. Handles for fast paths,
                  JSON for bulk queries like "dump the whole object tree".

  Why the object tree matters:
    "mob." needs every proc/var on /mob plus everything inherited plus BYOND
    builtins. "var/mob/test/t" then "t." reads the type straight out of the
    declaration. Both are object tree lookups, not type inference.

CHALLENGES
--------------------------------------------------------------------------------
  - Builtins. mob.Move(), .loc, .client exist nowhere in user code. Without a
    bundled definition file, "mob." only shows what we wrote. Must scrape the
    BYOND reference HTML. Unglamorous and easy to underestimate.
  - Preprocessor source maps. If expanded tokens don't remember where they came
    from, every completion and error lands on the wrong line. Most real DM is
    macro-heavy, so this is not optional.
  - Parser error recovery. Editor buffers are broken on every keystroke. A
    parser that stops at the first error is useless here.
  - Include order is semantic. DM resolves overrides by .dme include order, so
    the include graph must stay ordered, and editing a #define invalidates
    everything downstream.
  - String interpolation. "text[expr]more" means the lexer re-enters expression
    mode recursively.
  - The ":" operator deliberately skips type checking. Completion after ":"
    must show everything. Filtering it is a bug.
  - Nesting block comments. DM nests /* */, unlike C.
  - Dots and slashes. See PLAN.md section 4a. The short version:
      Mid-path, "." and "/" are the SAME token. /obj/item.sword == /obj/item/sword
      "proc" and "verb" are ordinary path segments, not keywords.
      "proc/" means declare-new. Leaving it off means override.
      var declarations also accept a SPACE as a separator (but not in for-headers).
      In expressions, leading "/" is absolute and leading "." is an upward
        SEARCH from the current type to root, first hit wins.
      No leading separator at all means it was never a path - it's member access.
      "//" inside a path is a comment. /obj//item evaluates to /obj.
      C-style for uses COMMAS: for(var/i = 1, i <= 5, i++)
  - Worst one: "var.thing.T" parses differently depending on whether /thing was
    already declared at that point in include order. Swapping two #include lines
    flips it. We match the compiler and warn, rather than diverging.
  - DM has BOTH brace blocks and significant indentation, mixed in one file.
  - Operator overloading: operator+, operator:=, operator_turn. Note that
    "operator:=" contains a colon, so naive ":" lexing splits it wrongly.
  - Stringification (#arg) exists, and shows up inside string interpolation:
      #define ASSERT(c) if(!(c)) { CRASH("...Assertion Failed: [#c]"); }
  - Odd but legal declaration forms we must handle:
      var/a=1,b=0,c=0           comma-separated var lists
      x = 0; y = 0; z = 0       semicolons separate statements on one line
      Multiply(m) return ...    proc body on the signature line
      MapColors(a, j=0, k=0)    default parameter values
      _dm_interface = FLAGS     inherited var override, no var/ keyword
  - Position encoding. LSP wants UTF-16 offsets, the C ABI wants UTF-8 bytes.
    Support both from day one or retrofit every service signature later.
  - NativeAOT constraints. No reflection or dynamic in Dm.Core. Exceptions must
    never cross the C boundary. Per-platform binaries mean a CI build matrix.
  - We become the platform. Two IDEs depend on our ABI, so breaking changes
    cost other people real work.
